## 1. 제품 개요

**제품명: JobFit** — 채용공고 기반 커리어 매칭 플랫폼

한 줄 정의:
> 흩어진 채용공고를 수집·구조화하고, 구직자 프로필과의 **적합도를 점수로 산출**하며,
> **부족한 스킬과 학습 경로까지 제안**하는 AI 커리어 매칭 서비스.

---

## 2. 문제 정의 (Why)

| # | 문제 | 현재 상황 | 근거 |
|---|---|---|---|
| P1 | 공고 탐색 비용이 크다 | 구직자는 수백 개 공고를 눈으로 읽고 "내가 될까?"를 감으로 판단 | 키워드 검색은 `Python`을 쳐도 "Python 우대"와 "Python 필수"를 구분 못 함 |
| P2 | 자격요건이 비정형 텍스트 | "3년 이상 경력, RDBMS 이해, 대용량 처리 경험 우대" → 내 스킬과 대조 불가 | 공고 본문은 자유 서술 형식 |
| P3 | 갭이 보이지 않는다 | 떨어져도 "무엇이 부족했는지" 알 수 없음 | 피드백 루프 부재 |
| P4 | 커리어 경로가 안 보인다 | "데이터 엔지니어가 되려면 지금 뭘 해야 하나" 답을 못 얻음 | 공고 데이터는 있지만 개인화된 해석이 없음 |

## 3. 해결 방식 (What)

```
채용공고(원문)                사용자 프로필
      │                              │
      ▼                              ▼
 ① 수집·정규화              ① 스킬/경력 구조화
      │                              │
      ▼                              │
 ② 스킬 추출 (사전+규칙→LLM)          │
      │                              │
      ├──────────┬──────────┬────────┘
      ▼          ▼          ▼
 ③ 임베딩    ④ 적합도 모델  ⑤ 스킬 갭 분석
 (의미검색)   (ML 점수)     (부족 스킬 Top-N)
      │          │          │
      └──────────┴──────────┘
                 ▼
      ⑥ RAG 상담 (근거 공고 인용)
                 ▼
      ⑦ 에이전트 (커리어 로드맵 생성)
```

핵심 차별점 3가지:
1. **점수 + 근거**: "적합도 78점"이 아니라 "78점 — 필수 스킬 5개 중 4개 보유, 경력 3년 요구에 2.5년(근접), Airflow 미보유"
2. **의미 검색**: "대용량 배치 처리하는 백엔드" 같은 자연어로 검색 (임베딩 기반)
3. **실행 가능한 갭**: 부족 스킬 → 그 스킬이 등장하는 공고 수 → 학습 우선순위

## 4. 페르소나 & 유스케이스

### 페르소나
- **P1. 취준생 민서 (26세, 비전공 → 데이터 직군 준비 1년차)**
  - 니즈: "내 수준으로 지원 가능한 공고가 있긴 한가?" / "뭘 더 배워야 하나?"
- **P2. 이직 고민 중인 준호 (31세, 백엔드 3년차)**
  - 니즈: "내 경력으로 갈 수 있는 더 좋은 곳은?" / "데이터 엔지니어로 전환 가능한가?"

### 핵심 유스케이스

| ID | 이름 | 시나리오 | 관련 Phase |
|---|---|---|---|
| UC1 | 공고 탐색 | 지역·경력·직무 필터 + 자연어 검색으로 공고 목록 조회 | 1, 3, 4 |
| UC2 | 적합도 진단 | 프로필 입력 → 적합도 상위 20개 공고 + 점수 + 근거 표시 | 2, 4 |
| UC3 | 스킬 갭 분석 | 목표 직무 선택 → 시장 요구 스킬 대비 내 부족 스킬 Top-5 + 학습 우선순위 | 1, 2 |
| UC4 | 커리어 Q&A | "내 프로필로 갈 만한 데이터 엔지니어 공고 알려줘" → 근거 공고 인용 답변 | 4 |
| UC5 | 커리어 플랜 | 에이전트가 프로필 분석 → 시장 조사 → 갭 분석 → 6개월 학습 로드맵 생성 | 6 |

## 5. 범위 (Scope)

### In Scope
- 한국어 채용공고 (고용24/워크넷 공공데이터 OpenAPI)
- 웹 API (FastAPI) + 최소한의 데모 UI (HTML/Jinja 또는 Streamlit 수준)
- 단일 노드 배포 (Oracle Cloud Always Free, ARM64)
- 개인 프로젝트 규모: 공고 1만~5만 건, 동시 사용자 수십 명 수준

### 제약 — 데이터 라이선스 (2026-09-14 확인)
워크넷 채용정보 API는 **공공저작물 제4유형**(출처표시 + 상업적 이용금지 + 변경금지)이다.
- 개인 학습·포트폴리오 용도는 문제없음
- **수익화 불가**. 서비스화하려면 데이터 소스 교체 필요
- 공개 배포 시 출처(한국고용정보원 워크넷) 명시 의무
→ 상세는 [api-work24.md](api-work24.md)

### Out of Scope (명시적 제외)
- 실제 기업 ATS 연동 / 지원서 대행 제출
- 모바일 네이티브 앱
- 다국어 (한국어 우선, 임베딩 모델은 다국어지만 UX는 한국어)
- 결제/구독
- 대규모 크롤링 (법적 리스크 회피, 공공 API만 사용)

## 6. 성공 지표 (Definition of Success)

| 영역 | 지표 | 목표 | 측정 시점 |
|---|---|---|---|
| 데이터 | 적재 공고 수 | 10,000건+ | Phase 1 종료 |
| 데이터 | 일일 수집 작업 성공률 | ≥ 99% | Phase 7 |
| 데이터 | 스킬 추출 정밀도 (수동 검수 200건) | Precision ≥ 0.85 | Phase 1 종료 |
| ML | 적합도 모델 AUC | ≥ 0.75 | Phase 2 |
| ML | 랭킹 nDCG@10 | ≥ 0.70 | Phase 2 |
| 검색 | 의미검색 Recall@10 (수동 라벨 100쿼리) | ≥ 0.80 | Phase 3 |
| RAG | RAGAS faithfulness | ≥ 0.80 | Phase 4 |
| RAG | RAGAS answer_relevancy | ≥ 0.80 | Phase 4 |
| 서비스 | 검색 API p95 지연 | < 1.5s | Phase 5 |
| 서비스 | 가용성 (단일 노드) | ≥ 99% / 주 | Phase 7 |
| 운영 | CI 파이프라인 통과율 | 100% (main 브랜치) | Phase 0부터 상시 |

## 7. 학습 목표 (이 프로젝트의 진짜 목적)

이 프로젝트는 **"AI 엔지니어의 전체 흐름을 탑다운으로 체험"**하는 것이 1차 목표입니다.
각 Phase에서 아래를 몸으로 익히는 것이 성공 기준입니다.

| Phase | 체득 목표 |
|---|---|
| 0 | 컨테이너로 개발환경을 재현하고, CI가 내 코드를 검증하게 만든다 |
| 1 | 외부 데이터를 신뢰 가능한 테이블로 만드는 ETL을 직접 설계한다 |
| 2 | 피처를 만들고, 모델을 학습하고, 실험을 기록·비교한다 |
| 3 | 텍스트를 벡터로 바꾸고 벡터DB로 의미 검색을 구현한다 |
| 4 | 검색 + LLM을 결합한 RAG를 만들고 **정량 평가**한다 |
| 5 | 서비스의 상태를 지표와 대시보드로 관찰한다 |
| 6 | 여러 단계를 스스로 판단하는 에이전트를 만들고, 인증으로 보호한다 |
| 7 | 스케줄링·배포까지 붙여 "돌아가는 시스템"으로 만든다 |

## 8. 주요 제약 & 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 공공 API의 IT 직군 공고가 적을 수 있음 | 매칭 품질 저하 | Phase 1에서 실데이터 확인 후, 부족하면 직무 범위를 IT→사무/기술 전반으로 확장 |
| 로컬이 CPU-only | 임베딩/LLM 느림 | e5-small(384d, CPU 가능) 채택, LLM은 Phase 4에서 API 우선 → Phase 7에서 Ollama 소형 모델 |
| Oracle ARM64 | 일부 wheel 미제공 | Phase 0에서 ARM64 빌드 검증, 문제 시 컨테이너 내 소스 빌드 |
| Python 3.14 (로컬 설치본) | ML 라이브러리 wheel 미지원 가능성 높음 | **Python 3.12로 통일** (Docker 이미지 + 로컬 venv 모두) |
| 사용자 상호작용 데이터 없음 (콜드 스타트) | 지도학습 라벨 부재 | Phase 2에서 룰 기반 pseudo-label + 소량 수동 라벨로 시작 |

## 9. 진행 방식 (Working Agreement)

1. 문서(`docs/`)가 항상 진실의 원천. 설계 변경은 문서를 먼저 고친다.
2. Phase 단위로 진행하며, 각 Phase는 **DoD(Definition of Done)** 를 만족해야 다음으로 넘어간다.
3. Claude가 설계·설명·코드 초안을 제공하고, **사용자가 직접 입력·실행·디버깅**한다.
4. 각 단계마다 "왜 이 기술인가 / 대안은 무엇인가"를 먼저 설명한다.
5. 막히면 되돌아가지 말고, 최소 동작 버전을 먼저 만든 뒤 개선한다.
