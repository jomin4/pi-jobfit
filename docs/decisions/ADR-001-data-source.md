# ADR-001. 채용 데이터 소스로 사람인 Open API를 채택한다

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-15
- **관련**: [api-work24.md](../api-work24.md), [00-charter.md](../00-charter.md), [04-roadmap.md](../04-roadmap.md)

---

## 배경 (Context)

기획 단계에서 데이터 소스를 **고용24(워크넷) 공공데이터 OpenAPI** 로 정했다.
근거는 "합법적이고 안정적이며 무료"였다. 크롤링은 법적 리스크로 배제했다.

작업 1.1에서 인증키를 발급받아 실제로 호출해보니 다음 벽에 막혔다.

```xml
<GO24><error>개인회원은 사용할 수 없는 OPEN-API입니다.</error></GO24>
```

에러 메시지가 3단계로 바뀌며 원인이 좁혀졌다.

| 단계 | 응답 | 해석 |
|---|---|---|
| 1 | `authKey는 필수 입니다` | 파라미터 문제 |
| 2 | `신청하신 OpenApi 서비스가 존재하지 않습니다` | 키는 유효, API 미신청 |
| 3 | `개인회원은 사용할 수 없는 OPEN-API입니다` | **계정 등급 미달** |

### 우회로 확인 결과 — 없음
- 레거시 워크넷 OpenAPI(`openapi.work.go.kr/opiMain.do`) → **서비스 종료**
  > "워크넷 OPEN-API서비스가 고용24 OPEN-API로 통합되었습니다"
- 공공데이터포털(data.go.kr 3038225) → **LINK 유형**. 포털이 중계하지 않고
  고용24 서버를 직접 호출하므로 동일한 제한을 받는다.

즉 **사업자등록번호를 가진 기업회원**이 되지 않는 한 이 API는 쓸 수 없다.

## 검토한 대안

| # | 안 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 사업자등록 후 고용24 기업회원 | 원설계 그대로. `jobCont` 본문 확보 | 학습 프로젝트에 세금·보험 등 실생활 의무가 따라옴 | ❌ 과함 |
| B | **사람인 Open API** | 개인 신청 가능. **민간 IT 공고**라 주제 적합도가 오히려 높음 | 일 500호출 제한, 비상업 조건, 본문 포함 여부 미확인 | ✅ **채택** |
| C | 공공기관 채용(잡알리오) 등 | 공공 데이터, 개인 사용 가능 | IT 직군 공고 수가 적음 | ❌ |
| D | 합성/샘플 데이터 | 즉시 시작, 일정 리스크 0 | 실데이터 감각 상실 | ❌ 사용자가 거부 |

## 결정 (Decision)

**사람인 Open API (`https://oapi.saramin.co.kr/job-search`) 를 1차 데이터 소스로 채택한다.**

사용자의 방침: *"적은 데이터더라도 샘플 데이터 대신 실제 데이터로 진행한다."*

### 채택 근거
1. **개인 개발자가 신청 가능하다** — 유일하게 벽이 없는 실데이터 소스
2. **주제 적합도가 오히려 더 높다** — 공공 API는 IT 직군 비중이 낮지만,
   사람인은 민간 IT 채용이 주력이다. "커리어 매칭" 대상으로 더 현실적이다
3. 구조화 수준이 높다 — 직무코드·산업코드·경력·학력·연봉 코드 체계 제공
4. 증분 수집 지원 — `published_min/max`, `updated_min/max`

## 제약 (Consequences)

### 지켜야 할 이용 조건
| 조건 | 내용 | 대응 |
|---|---|---|
| 호출 한도 | **일 최대 500회** | 호출 예산 관리 필수 (아래 참조) |
| 비상업 | 재판매·이용요금 발생 금지 | 학습/포트폴리오 용도로 한정 |
| 출처 표기 | `Powered by 취업 사람인` 명시 | README + API 응답 + 데모 UI에 표기 |
| 베타 | 인터페이스 변경 가능 | Raw 레이어 보존 + collector 격리로 흡수 |

### 호출 예산 계산
```
회당 최대 110건 × 일 500회 = 이론상 55,000건/일
안전 마진 고려 → 일 300회(33,000건)를 상한으로 운용
```
고용24 대비 **오히려 여유롭다.** 고용24는 상세를 건별로 호출해야 했지만(N+1),
사람인은 목록 응답에 필요한 필드가 함께 온다.

### 아직 모르는 것 ⚠️
**응답에 공고 본문(직무내용) 전문이 포함되는지 확인되지 않았다.**
명세 페이지가 로그인 뒤에 있어 승인 전에는 알 수 없다.

- 포함된다면 → 원설계(본문 → 스킬 추출) 그대로 진행
- 키워드 필드만 있다면 → `position.keyword` 를 1차 스킬 신호로 쓰고,
  `title` + `job_code` + `industry` 를 보조 피처로 사용.
  스킬 추출은 "본문 NER"이 아니라 "키워드 정규화 + 온톨로지 매핑"으로 성격이 바뀐다.

→ **승인 직후 첫 응답 1건을 저장해 확인하고, 그 결과를 이 ADR에 추가한다.**

## 설계에 반영할 것

1. **Collector 인터페이스를 소스 중립으로 만든다**
   ```
   src/jobfit/collectors/
     base.py        JobCollector 프로토콜 (fetch_list / fetch_detail)
     saramin.py     사람인 구현      ← 지금 만든다
     work24.py      고용24 구현      ← 기업회원 전환 시 추가
   ```
   Raw 레이어에 `source` 컬럼을 이미 두었으므로 **여러 소스 동시 운용이 가능**하다.
   설계 당시 의도한 확장점이 실제로 값을 했다.

2. **호출 예산을 코드로 강제한다**
   일일 호출 카운터를 Redis에 두고 상한 초과 시 태스크를 중단한다.
   외부 API 한도를 코드가 모르면 언젠가 반드시 넘긴다.

3. **`03-data-model.md` 의 `jobs` 스키마는 유지한다**
   사람인 필드도 동일 스키마에 매핑 가능하다. 소스가 바뀌어도 하위 레이어는 그대로다 —
   이것이 Raw/Silver/Gold 분리를 택한 이유다.
