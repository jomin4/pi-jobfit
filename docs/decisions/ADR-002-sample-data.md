# ADR-002. 샘플 데이터로 파이프라인을 먼저 완성하고 나중에 실데이터로 교체한다

- **상태**: 채택 (Accepted)
- **일자**: 2026-09-15
- **관련**: [ADR-001](ADR-001-data-source.md), [api-work24.md](../api-work24.md)

---

## 배경

[ADR-001](ADR-001-data-source.md)에서 사람인 API로 전환했으나, 승인 대기와 응답 스키마 불확실성이
남아 있었다. 사용자는 **고용24 API를 최종 목표로 유지**하되(기업회원 전환은 추후 판단),
그때까지 **샘플 데이터로 프로그램을 완성**하고 이후 실데이터로 마이그레이션하기로 결정했다.

## 결정

**고용24 응답 스키마와 동일한 형태의 샘플 데이터를, `SampleCollector` 라는 수집기로 생성한다.**

CSV나 임의 JSON이 아니다. `<wantedDtl>` 구조·필드명·코드값을 그대로 쓴다.
[api-work24.md](../api-work24.md)에서 명세 전체를 확보했기 때문에 가능하다.

```
SampleCollector  ──┐
                   ├──→ raw_job_postings ──→ 정규화 ──→ jobs ──→ ...
Work24Collector ──┘        (source='sample' / 'work24')
```

교체 비용은 **`collectors/` 파일 하나**다. 하위 레이어는 손대지 않는다.

## 샘플 데이터의 5가지 기준

### 1. 스키마 충실성
학력 `04`, 경력 `E`, 임금형태 `Y` 등 **실제 코드값**을 그대로 쓴다.
코드→값 매핑 로직이 실데이터에서도 그대로 동작해야 한다.

### 2. 분포 현실성
균등 분포는 모델이 배울 게 없다. 실제 시장의 편중을 재현한다.

| 항목 | 목표 | 실측(2,500건) |
|---|---|---|
| 서울 비중 | 55% | 55.6% |
| 급여 미기재 | 45% | 46% |
| 상시채용 | 30% | 29% |

> ⚠️ 이 목표 수치는 **추정치**다. 실측 데이터가 아니다.
> 실데이터 확보 시 대조해서 보정해야 한다.

### 3. 지저분함
깨끗한 샘플로 만든 파서는 실데이터에서 전부 터진다. 의도적으로 더럽힌다.

| 함정 | 예 |
|---|---|
| 급여 | `회사내규에 따름`, `면접 후 결정`, `연 6900~8500만원`, `월 280만원` |
| 경력 | `경력무관`, `신입/경력`, `경력 36개월 이상` |
| 마감 | `상시채용`, `2026.10.21`, `2026/10/21` |
| 회사명 | `(주)X`, `X(주)`, `X 주식회사`, `㈜X`, `X` — 30개 법인 × 5형태 = 150개 표기 |
| 본문 오염 | `<br>`, `&nbsp;`, 과한 줄바꿈 |
| 결측 | 본문 7%, 자격요건 65%, 우대사항 20%가 빈 값 |

### 4. 규모 — 2,500건
실데이터 목표(10,000건)보다 작다. **CPU 임베딩 시간이 곧 실험 비용**이기 때문이다.
e5-small 기준 2,500건은 노트북에서 5~10분, 10,000건은 30분 이상이라 반복 실험을 방해한다.
Phase 2 ML은 프로필 20개 × 공고 2,500 = 50,000쌍이라 학습에 충분하다.

### 5. 재현성 — 파일이 아니라 생성기를 커밋
`seed` 고정으로 누가 언제 돌려도 같은 데이터가 나온다.
생성물(`data/raw/sample/`)은 `.gitignore` 대상이고, 생성기와 어휘 사전만 커밋한다.

## 평가의 순환 논리 문제와 대응

**"내가 Python을 넣었으니 추출기가 Python을 찾는다"** 는 아무것도 증명하지 못한다.
Phase 1 DoD의 "스킬 추출 정밀도 ≥ 0.85"가 자동 달성되는 가짜 성공이 된다.

### 대응 1 — 표준명을 그대로 쓰지 않는다
| 장치 | 예 |
|---|---|
| 별칭 | `TypeScript` → `ts`, `Next.js` → `넥스트js`, `Figma` → `피그마` |
| 오타 | `Node.js` → `ndoejs` (인접 문자 교환) |
| 함정어 | `R&D 조직과 협업`(R 아님), `C 레벨 임원`(C 아님), `Go 사업부`(Go 아님) |
| 부정 문맥 | `Python 경험 무관`, `Java 경험은 필수가 아닙니다` |

실측 난이도(500건 기준):

```
정답 스킬 2,260개 중
  표준명 그대로 등장 : 78%
  별칭으로만 등장    : 20%   <- 별칭 처리 못 하면 여기서 막힌다
  오타로 훼손됨      :  2%   <- 현실적 상한선
```

**별칭 사전 없이는 78%가 천장**이고, 오타 2%가 recall 상한을 만든다. 정직한 평가가 된다.

### 대응 2 — 정답은 "실제로 쓰인 스킬"만
생성 시점에 `GroundTruth(required, preferred)` 를 기록하되,
**본문·자격요건·키워드에 실제로 등장한 스킬만** 정답에 넣는다.

초기 구현은 `required` 4개를 뽑고 본문에는 3개만 쓰는 버그가 있었다.
남은 1개는 어디에도 없어 추출기가 절대 못 맞히는 정답이 되어 점수를 왜곡했다.

## 수집기 계층 설계

```
src/jobfit/collectors/
├── base.py     RawDocument / ListQuery / ListPage / JobCollector(ABC)
├── budget.py   CallBudget / UnlimitedBudget / RedisDailyBudget
└── sample.py   SampleCollector          (work24.py 는 나중)
```

**핵심: 정책은 베이스가 강제하고, 구현체는 "가져오기"만 한다.**

| 정책 | 어디서 | 왜 |
|---|---|---|
| 일일 호출 예산 | `JobCollector.fetch_list/fetch_detail` | 구현체가 예산 차감을 잊을 수 없게 |
| 개인정보 제거 | `JobCollector._document` | Raw는 불변이라 **적재 전에** 잘라야 함 |
| 내용 해시 | `RawDocument.hash` | 중복 판정 기준을 한 곳에서 |
| 페이징 | `JobCollector.iter_list` | 호출자가 페이지 계산을 안 하게 |

새 소스를 붙일 때 구현할 것은 `_fetch_list` / `_fetch_detail` 두 개뿐이다.

`ListQuery` 는 소스별 파라미터 이름 차이(고용24 `occupation` / 사람인 `job_cd`)를 흡수한다.

## 결과와 제약

- `source='sample'` 로 저장되므로 실데이터와 **한 DB에 공존**한다. 나중에 `DELETE WHERE source='sample'`.
- 회사명은 **전부 가상**이다. 실존 기업명을 쓰면 "그 회사가 이 공고를 냈다"는 오해를 만든다.
- **분포 추정치는 검증되지 않았다.** Phase 2 모델 성능이 실데이터에서 재현된다는 보장이 없다.
  이것이 이 결정의 가장 큰 위험이며, 실데이터 확보 시 가장 먼저 대조해야 한다.
- 공고 "수정 이력"(같은 `source_id` 의 내용 변경)은 아직 생성하지 않는다.
  `content_hash` 변경 감지를 제대로 시험하려면 나중에 추가해야 한다.
